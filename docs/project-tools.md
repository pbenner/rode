# Project tools

## Git source control

Use the **Source control** activity icon, **View → Source control**, or **Ctrl+Shift+G**. Git runs on the project host using its installed Git and configuration. The native panel provides:

- Status, branch/upstream information, working/staged diffs, and file or individual text-hunk staging/unstaging.
- Commits, amend, the latest 100 commits with patches, blame, cherry-pick, and revert.
- Branch creation/switching/deletion, merge/rebase, stash push/apply/pop/drop, and conflict-resolution controls.
- Fetch, fast-forward-only pull, push/upstream setup, remotes, tags, and submodule initialization/update.
- Worktree listing, creation with new or existing branches, opening, removal, and metadata pruning.
- Repository initialization and cloning into an empty selected project directory.

Changed files use single rows with aligned actions beside the filename. The list fills the pane and keeps its width while scrolling. In narrow panes, **Diff** and **Stage / Mark resolved** remain beside each file; **More** contains **Staged diff**, **Unstage** and **Discard**. Unavailable actions are disabled, and hovering a shortened filename shows its full path.

Actions follow the loaded index and working-tree status. **Stage** is available for unstaged/untracked changes; **Unstage** and **Staged diff** require resolved staged changes. A partially staged file offers both sides. **Diff** requires working-tree changes, and **Discard** is limited to tracked working-tree modifications, deletions or type changes. Conflicts offer **Mark resolved** after editing/saving; staged-only actions and Discard remain unavailable until resolution. **Stage all** and **Unstage all** follow the same rules. Actions wait for an in-flight Git operation and its status refresh to finish, and disabled controls explain their requirements on hover.

Open conflicted files, edit the conflict markers, save, and **Mark resolved**, then continue the merge/rebase. Changes shown by Git are on disk; save modified editor buffers before staging or changing branches. Discard, branch/tag deletion, stash removal, revert, rebase, and worktree removal expose a confirmation; normal Git protections remain in force. Hunk staging is available for ordinary tracked text patches; use whole-file staging for new/deleted/renamed/binary files.

Git operations run in background workers, with bounded output/time and no automatic fetch. The Changes panel refreshes while visible. Network actions use existing host credentials and report failures; **Git terminal** provides interactive authentication and arbitrary Git commands. Within bwrap, enable network access and explicitly grant any identity/agent paths your Git authentication requires. Global Git configuration is shared read-only by default and can be hidden in the access editor.

Stash actions capture the full object ID shown in the loaded list. Apply uses that immutable object; removal checks the selector and object together while holding Git's writer locks. If another terminal changes the list, refresh before removing the entry. A successful apply followed by a changed list leaves the saved stash in place and reports that pop could not remove it. Guarded removal supports Git's files reference backend, loose/packed stash refs, SHA-1/SHA-256 and linked worktrees. Reftable and namespaced repositories require the Git terminal for removal. Final-reference deletion uses Git's `hook run` command and honors reference-transaction hook rejection.

Git owns the removal transaction's locks. If the desktop or SSH helper exits, its control pipe closes and Git aborts the transaction, releasing those locks.

Linked worktrees share repository metadata. **Open + share main .git** explicitly grants that metadata directory when opening a separate worktree sandbox; **Open project** keeps the current/saved policy. Standard repository layouts are supported by the shortcut; nonstandard Git directories can be granted through the path editor. Worktree creation needs a destination accessible to the current sandbox.

## Formatting, issues, and Python environments

The **Environment** activity icon, workspace tab, status-bar control, or **Environment: Runtimes and project variables** command opens project-wide environment settings. Runtime overrides select installed Node.js/npm, Rust/Cargo, Go, Java and .NET executables on the project host. Blank entries retain PATH and the tool's project configuration. **Refresh runtime versions** probes the applied settings inside the active sandbox; it does not install runtimes. Runtime paths must already be accessible under that sandbox.

**Project variables** accepts literal `NAME=value` lines, without shell expansion. **Apply environment** saves runtime overrides and variables per host/project in local preferences. They apply to new terminals and task commands; existing or reattached terminals keep their original environment. Task exports are scoped to a subshell, so they do not change an existing shell's environment. Runtime overrides and project variables configure terminal/task execution, not agent processes, formatter workers or debugger adapters. Python interpreter selection retains its existing integrations with those tools.

The collapsible **Python interpreter and virtual environments** section retains Python's interpreter selection and venv creation. It opens by default for an active Python file. The legacy **Python: Select environment** command opens this section directly. Auto mode detects `.venv`, `venv`, `env`, or `.env` directly in the project, then uses system Python. Choose a discovered environment, enter a custom interpreter/environment path on the project host, or create a new environment with `python -m venv`. Existing destinations are never overwritten. Disable **Include pip** on hosts without `ensurepip`.

Interpreter choices are saved per host/project. New terminals activate the selected environment; selecting another interpreter keeps an existing terminal running. Use **Activate in current shell** with an idle shell, or **New** to start another terminal. Enable **Persist** in its header if it should continue after exit. Reattaching an existing terminal preserves its environment and never injects activation commands into running work. The separate **Tasks** panel contains run/build actions for the active language, Cargo/Go/npm test actions, and a **Python tasks** section for REPL, pytest and package listing. These controls use the selected executable and saved project variables. Run/build/test commands use the project terminal; save files first and use an idle shell. Ruff runs as `uvx ruff` by default on the project host. RODE searches PATH, then the standard `~/.local/bin/uvx` location so non-interactive SSH sessions work with a user-local uv installation. In Project settings, select `auto` to prefer Ruff beside the chosen interpreter, then its Python module, then PATH. An explicit `ruff` executable or absolute path is also supported; the setting is an executable path or one of these known modes, not a shell command.

See [Programming languages](languages.md) for Go, JS/TS/web, C-family, and shell tools and run/build commands. Python formatting/checking uses the project's [Ruff configuration](https://docs.astral.sh/ruff/configuration/); Rust formatting uses `rustfmt`. Install [uv](https://docs.astral.sh/uv/getting-started/installation/) on the project host to use the default `uvx ruff` runner. uv may download Ruff into its isolated cache on first use; warm that cache before working without network access. RODE keeps the default uv tool registry under `~/.cache/uv/tools` (or `$UV_CACHE_DIR/tools`) so read-only `~/.local` mounts work, and respects an explicit `UV_TOOL_DIR`. Python environments and other packages are created or installed only through explicit actions. Install `rustfmt` with your Rust toolchain for Rust formatting. **Code → Format document** / **Shift+Alt+F**, **Check document**, and **Ruff: apply safe fixes** are available manually. Safe fixes explicitly disable unsafe fixes even if the project's Ruff configuration enables them.

Formatting/checking on save and supported-language checks after a 900 ms typing pause are enabled by default, with switches in Project settings. Checks use the current in-memory buffer. Issues appear as colored underlines, gutter marks/tooltips, and clickable entries in **Problems** / **Ctrl+Shift+M**. Live checks cover the active supported buffer up to 512 KiB; manual/save checks use the normal 8 MiB editing limit. Formatting results are applied only if the buffer and settings still match the submitted version. If new edits arrive, they remain intact. Missing/failed tools leave the buffer editable and allow the submitted save without formatting; Python syntax errors still produce diagnostics when Ruff can check them.

**Save tool settings** flushes changes to local app preferences immediately. Python issues use Ruff; Go, Prettier-supported formats, and shell files have parser syntax diagnostics. A general LSP client and Rust compiler diagnostics are not implemented.

## Host monitor

Use the **System monitor** activity icon, **View → System monitor**, or **System: Monitor** in the command palette. No project is required: the welcome screen can show your local computer's metrics. With an SSH workspace, it monitors that remote host once connected, even before a project folder is ready; offline SSH sessions show a reconnect message rather than local metrics.

The dashboard arranges CPU, memory and GPU cards in one, two or three columns as the window allows. Plots keep a 16:9 aspect ratio and cards have a bounded width, including in detached windows. Filled history plots show labelled percentage/time axes and current readings. CPU charts compare overall usage with the busiest core; GPU charts compare utilization with VRAM occupancy. Hover over a chart for sample values. Colours follow the selected theme. Swap, load/uptime, disk capacity, network throughput, and expandable core/process details below the charts are also available. Disk capacity describes the project's filesystem when a project is ready, or the host's root filesystem otherwise. The panel identifies the host, and changing hosts clears the previous samples.

NVIDIA metrics come from [nvidia-smi](https://docs.nvidia.com/deploy/nvidia-smi/); AMD metrics use the kernel's [DRM/sysfs counters](https://docs.kernel.org/gpu/amdgpu/index.html) when exposed. Available readings include usage, VRAM, temperature, and power. Other DRM GPUs are listed with the readings the driver exposes. Missing/unsupported readings are shown as unavailable. No GPU telemetry was exposed by the development host, so GPU parsing is covered with representative samples rather than a claimed hardware validation.

Monitoring is on demand, samples in background workers every two seconds by default (configurable 1–30 s), bounds history to 120 samples, and pauses when hidden. CPU/network rates need two recent samples. Charts use actual sample times and leave gaps for missing readings or long pauses; no history is collected while hidden. Process CPU percentages are lifetime averages from `ps`. Telemetry intentionally reads the host outside the project sandbox to show host counters and devices; project tools remain inside the selected sandbox.

## Slurm allocations

**View → Terminals & Slurm** lists your scheduler jobs and allocated GPU counts, with confirmed whole-allocation release. Use [native persistent terminals](terminals.md) for interactive jobs that should survive closing RODE; see the [Slurm workflow and host requirements](slurm.md). The host monitor measures physical utilization separately.
