# Agent chat

Open **View → Agent chat**, use the speech-bubble activity icon, or press **Ctrl+Shift+A**. Choose a provider and open its settings button. Send a message with **Send** or **Enter**; **Shift+Enter** inserts a newline. Replies stream into the chat with Markdown headings, emphasis, lists, inline code and fenced code blocks. Text remains selectable across prose and code, with copy buttons and expandable tool results. Permission requests appear above the conversation; structured questions open a dedicated answer form.

When Codex asks a structured question, choose one of its suggested answers or type your own, then click **Send answers**. Choice explanations are shown below their labels. Every question needs an answer; selecting an option does not send it automatically. The form temporarily replaces the normal composer, preserving its draft, attachments and queued follow-ups. **Stop** cancels the pending request and interrupts the turn. Unanswered questions remain available after reattaching a persistent agent. Blocking requests show **Waiting for you**; non-blocking questions say that the agent can continue independent work. Requests cleared by Codex disappear rather than accepting a stale answer.

RODE opts into Codex's experimental app-server question API and enables `features.default_mode_request_user_input` for its own Codex process, so questions are available during ordinary coding turns. It does not change your Codex configuration files or permission policy. A question written only as ordinary assistant text is still answered through the normal composer after the turn ends; RODE does not infer tool requests from punctuation.

Use **Attach…** beside Send to add images, PDFs, or UTF-8 documents (text, Markdown, source, CSV, JSON, and similar files). Attached files appear above the input; **×** removes a file before sending. You can send files with or without a typed message. Queuing a message keeps its own immutable file snapshots, so changing the original file or composing another prompt does not alter that queued message. Failed reads leave your draft and existing attachments intact.

The picker defaults to **This computer**. In an SSH workspace, choose **Project host** to browse remote files under the active project policy instead. Contents travel with the prompt, so desktop paths do not need to exist on the SSH host. Images use native image inputs in [Codex](https://learn.chatgpt.com/docs/app-server) and image-capable [ACP agents](https://agentclientprotocol.com/protocol/v1/content); ACP agents that do not advertise image support report an error. Local models must also support images.

PDFs contribute their extracted text using desktop Poppler (`pdftotext`, included in `poppler-utils`); page artwork and scanned-only PDFs need image attachments or OCR text. Other documents must contain UTF-8 text; formats such as DOCX/XLSX must first be exported to text or PDF. Files are read in background workers, capped at 32 MiB each. Images are normalized to PNG/JPEG, at most 2048 pixels on the longest side, then reduced further if needed to fit 1 MiB of encoded data. Document text is limited to 1 MiB. Each message accepts at most eight files and 2 MiB of serialized attachment content; oversized documents are rejected rather than truncated. Attachments are not saved in RODE preferences. New chat and project/conversation changes clear unsent files; the agent backend may retain submitted content in its own conversation history. Background agents created by an older RODE version need a new chat before they can accept attachments.

**Copy response** copies the displayed message text, including code contents but excluding Markdown code fences and their language labels.

Drag the divider above **Model** and **Access** to resize the message input; double-click it to reset the height. Tab to the divider and use **Up/Down** to resize or **Home** to reset with the keyboard. Long drafts scroll independently using the mouse wheel, trackpad or scrollbar. Typing and cursor movement keep the caret visible, while Send/Stop stay outside the scrolling text. The preferred height is kept for the current window and adapts when the window gets smaller; history temporarily hides the input without clearing it.

At the start of the message box (**Ctrl+Home**), press **Up** repeatedly to browse older sent prompts and **Down** for newer ones. Down past the newest restores your unsent draft. RODE keeps all prompts submitted in the current window independently of the rolling display transcript, so long replies and tool output do not remove them from input history. Restoring or reattaching a chat also restores a separate recent-prompt history (up to 128 prompts / 512 KiB of serialized data), including loaded prompts whose display rows were evicted by tool output. New submissions extend that history. Saved prompts over the 32 KiB input limit remain browsable with an explicit truncation marker. These histories stay in memory until you change conversations; older host services fall back to the prompts still in their display transcript.

The agent starts in the opened project folder, on the computer hosting that project. The panel identifies **LOCAL** or **SSH**, the folder, and the actual sandbox mode. Hover the host/mode row for applied network/read-only details or the reason a requested sandbox could not start; this remains available in a detached chat window. Without an opened folder, it uses RODE's startup working directory. Opening the panel starts no process. Sending a message or explicitly opening **History** starts the selected agent; history browsing sends no model prompt.

**New chat** stays visible but disabled while the current agent is working, stopping or being reattached. Use **Stop** to interrupt active work, then wait until the agent is idle before starting a new conversation. Clicking New chat cannot discard an active turn or its queued work.

## Queued follow-ups

While the agent is working, **Enter** or **Queue** adds your message to the queue above the composer. Follow-ups run one at a time, in order, after a successful reply. They do not interrupt the current task. **Shift+Enter** still inserts a newline.

Prompt recall keeps submitted text independently of the rolling display transcript. Recent queued submissions also carry a bounded dispatch record, so tool output cannot erase them before the desktop observes their completion.

After reattaching a Codex chat, keep pressing **Up** at the start of the input to reach earlier prompts. When the recent cache ends, RODE reads older user messages from the saved conversation in small pages; the 128-prompt / 512-KiB host snapshot is an IPC limit, not a limit on how far back you can browse. This also recovers prompts missing from older running services' trimmed transcripts. Reading does not resume the thread, take ownership from the live agent, or send a model request. Consecutive identical prompts remain separate entries, and **Down** returns to your unsent draft. Typing or pressing Down while an older page loads cancels the pending jump without discarding the fetched history. Other providers retain the prompts supplied by their live controller; older-history pagination currently uses Codex's read-only history API.

Use **↑ / ↓** to reorder prompts, **Edit** to change one, or **Delete** to remove it. Editing waits for **Save prompt** or **Cancel edit** before dispatch continues, without changing the draft in your main message box. **Pause queue / Resume queue** controls automatic sending. **Stop**, a failed turn or losing the agent backend pauses remaining prompts; resume them explicitly when ready. Queued prompts use the latest settings acknowledged by the host, including model, permissions and response style. Losing the desktop/SSH view does not pause a persistent agent's queue.

The queue holds up to 16 messages for the current conversation, including immutable attachment snapshots. The native agent service owns and dispatches this queue and acknowledges edits/settings before a clean Rode exit. Moving Chat into a separate window, hiding it, or working in the editor does not stop dispatch. With **Persist: on**, queued prompts also continue after detaching, closing/restarting Rode, switching projects, choosing New chat or losing SSH. Reattach that agent through **Running** to restore its current progress, remaining queue, committed edits, pause state and files. Permission requests and edit holds still wait for explicit input; persistence never approves them. Prompts never move to a different conversation. Closing an agent with persistence off or explicitly ending it discards its queue; host/service shutdown also ends these in-memory queues. No queue contents are written to shared preferences. Start a new chat after upgrading to use automatic detached dispatch; existing agents retain their original service and older queues require an attached view.

## Model connection with offline tools

For Codex and **Codex · local model**, open the chat's **Access** menu and select **Agent networking → Model connection only**. First enable a project sandbox in **View → Project settings / sandbox access**, turn off **Allow network access**, and apply it. The sandbox must actually be active; unavailable enforcement or a network-enabled project policy prevents this agent mode from starting. Claude Code and other ACP providers do not currently support this mode.

The trusted Codex controller receives a network exception so model requests and authentication can work, including a model server on the project host's localhost. Its built-in shell, code execution, web search, browser, MCP, plugin and hook integrations are disabled and checked before a model turn starts. The controller retains the project's filesystem sandbox. Its network exception is not a destination firewall; it applies to the trusted controller, not to agent-generated programs.

RODE supplies its native project file tools and, with **Project access** or **Full access**, **rode_run_command**. Commands run under the original offline project policy, including all filesystem grants, and their children inherit it. They cannot gain networking through an approval. **Read only**, **Edit project files only**, and read-only projects do not receive the command tool. Prompts, relevant code and tool results still travel to the selected model provider.

Commands are noninteractive, with a default 30-second timeout, an explicit maximum of 120 seconds, at most 32 KiB of command text and 256 KiB of output per stream. Nonzero exit codes and diagnostics return to the agent; timeout, cancellation or output overflow stops the owned command process group. Prepare dependencies that need downloads separately in your own terminal. Shell commands retain the project's ordinary filesystem access; the native file tools additionally protect Git/Codex metadata and symlinks as described under file-only access.

Changing this setting starts a new agent session. Saved history can be browsed, but creating these native tools requires a fresh context; use **Running** to reattach a live persistent conversation. Recovery uses **Start new context** and keeps queued prompts without replaying the interrupted one. Update the native helper to use this mode over SSH. The `agent_offline_tools` capability and session protocol 14 select a compatible service; older sessions remain discoverable and keep their original policy.

## Background agents

Use **Persist: off/on** at the right of the chat's Send row. New chats default to **off**. Enable it before sending or during a task; the filled button appears after the host acknowledges the change. Turning it off again keeps the current task running until its controlling view closes. Choosing persistence alone starts no agent.

With persistence on, the native host service keeps the agent and its tool processes running when RODE exits, the project changes, or SSH disconnects. Open the original project with the same sandbox policy, click **Running** beside History (or **Agent: Running sessions** in the command palette), then **Attach**. Reattachment restores the live conversation, pending requests and actual model/access settings without restarting the backend. Each agent has one controlling window at a time; detach it before attaching elsewhere. The list can be inspected from other windows on the same host. **End → Confirm end** stops a session and its owned tools.

The Running window shows your current project and actual isolation mode alongside each agent's original project and mode. A disabled **Attach** shows a reason below Status, with a detailed explanation on hover: open the original project, restore its sandbox settings, detach the other controlling window, or enable persistence/stop the current chat before switching. Normal mode and sandbox mode are different policies; attaching cannot move a running agent between them. Matching mode labels alone are not enough if folder access, read-only or network settings have changed.

Policy comparison ignores RODE's temporary native-helper location, so reopening the same project with unchanged access rules can reattach its sessions. Older builds included that location in the policy identifier, causing false mismatches across project reopenings. Already-running sessions retain their original identifier and cannot be retroactively matched from their mode label alone. They remain running; sessions started with the updated build use the stable identity. This applies to both bubblewrap and Landlock, and to persistent terminals and runtimes that share the same policy check.

Permission requests wait while detached; persistence never approves them or widens the captured filesystem/network policy. **Stop** interrupts a turn. **Detach** leaves an idle persistent agent running. **New chat** releases the current view and returns persistence to off: an old persistent session remains in Running. Closing only the chat panel hides the view and continues work with either setting.

Live sessions are held by `rode-sessiond`, alongside persistent terminals, without tmux/screen or a remote GUI. Cargo installation includes this helper; SSH uses the verified [remote helper](terminals.md#remote-helper-and-packaging). The service exits after its last agent/PTY process has stopped. It retains at most 16 agent controllers per service generation and the same bounded recent transcript as the UI, in memory only. These live sessions do not survive host shutdown; **History** separately browses conversations saved by the backend. User-managed model servers and authentication must remain available. Encrypted projects must have their jobs stopped before they can lock; use Running → End for persistent agents.

## Model and access controls

Use **Model** and **Access** / **Permissions** above the message field. Choices are saved per host/project through the shared preference locks. Controls are disabled during active work. Stop the current turn before changing them.

For **Codex**, Model accepts an explicit model ID or the agent default. Opening **Model** loads the agent's model catalog and advertised reasoning efforts, including before the first message. This uses a short-lived metadata connection on the project host under its sandbox policy; it creates no conversation or model turn. The catalog is kept in memory for subsequent new chats in the same project. Discovery errors appear in the menu with **Retry model discovery**. Open **Reasoning effort** and choose **Default** or one of the model's advertised levels from its submenu. The choice is saved immediately and applies to the next message. Catalog entries describe available choices, not an account-entitlement guarantee. Custom model/effort IDs remain available when discovery is unsupported. For **Codex · local model**, enter the installed server model ID and an optional supported reasoning effort. Codex's cloud-oriented catalog is not used as an inventory of installed Ollama models.

Codex tool access offers **Read only**, **Edit project files only**, **Project access** (default), and **Full access**. Read only prevents approval-based tool escalation. Project access allows workspace writes and can request additional access. Full access uses the host permissions left inside the active project sandbox; in normal mode it uses the user's host permissions. The project's actual read-only restriction always takes precedence. These are agent tool policies, separate from the enclosing filesystem sandbox.

When RODE's project sandbox is actually active, the menu shows **Access: Project sandbox** for ordinary coding. **Project access** and **Full access** remain visible but disabled with a short explanation: both use RODE's enforced boundary instead of adding a duplicate Codex sandbox. **Use project sandbox** returns from a stricter mode to ordinary coding. **Read only**, **Edit project files only**, networking and permission-request settings remain available because they add distinct restrictions. Merely opening the menu preserves your saved normal-mode preference; explicitly choosing **Use project sandbox** saves **Project access**, so it does not grant full host access if sandboxing is later turned off. Without active enforcement, including when a sandbox probe fails, the ordinary access choices remain available. Claude/ACP controls remain provider-managed and are not automatically disabled.

### Edit project files only

Choose **Access → Edit project files only** with an open project. Codex can list directories, read and search UTF-8 source, create directories, and create/replace/delete source files through RODE's native file tools. Paths stay within that project on its **local or SSH host**. Run tests, builds, installations and Git commands yourself.

This mode disables Codex command execution, code execution, hooks, plugins, apps, browser/computer tools, subagents, notification commands and configured MCP servers. Project mise environment launchers are bypassed because they can evaluate project code. The controller checks effective Codex feature settings before submitting a model turn; an unsupported or conflicting configuration stops startup. Codex's built-in tools use read-only access with permission escalation declined. All writes go through the native file boundary. These are runtime controls, not a prompt asking the model to avoid commands.

The file boundary requires Linux `openat2` and Landlock filesystem support (ABI 1 or newer, Linux 5.13+ with Landlock enabled). It fails closed when either is unavailable. Each native helper also confines itself to the project with Landlock, so a concurrently moved directory cannot redirect an operation outside the root. There is no path-traversal or symlink fallback. Symlinks (including ones pointing inside the project), nested mounts, special/binary files, `.git`, `.codex`, and modifications to the active agent executable are unavailable. The effective `CODEX_HOME`, including custom names and host/mount aliases, is excluded from reads, listings, searches and edits. Expose a custom state location through the launch environment; a custom wrapper must not secretly relocate private state into the editable tree. Files are limited to 1 MiB. Reads return a content revision; replacements/deletions require that revision, and creates never overwrite existing files. Writes publish atomically and do not modify hard-linked files outside the project. Searches use literal text, scan at most 1,000 directory entries and read at most 8 MiB, including rejected binary content. Native operations run off the controller thread; Stop cancels their helpers and discards late results. Oversized encoded tool responses return an error without disconnecting the chat. An active project sandbox additionally enforces hidden/read-only subpaths, and a read-only project cannot be edited.

Private state protection requires an updated editor/native helper (`agent_private_state`, session protocol 15). New chats select a compatible service; existing chats retain their original controller and policy. End and restart older chats to apply this protection.

Executable protection uses the path selected for the actual launch, including host and sandbox mount aliases. Bare command names are resolved on the execution host; relative or empty `PATH` entries refer to the project working directory. The direct library transport rejects native file operations until that identity is available, rather than treating a configured command name as a project-relative filename.

Entering or leaving this mode starts a new Codex conversation. Live file-only chats can persist and be reattached through **Running** with their original restrictions. **History** remains available for browsing; saved-chat restore/deletion is disabled in this mode because older app-server history APIs cannot replace stored tool definitions safely. Switch modes or start a fresh file-only chat instead. ACP agents cannot claim this mode.

RODE still starts trusted native helpers and the configured Codex runtime; this mode removes agent-requested command execution, not operating-system process creation in general. Custom agent executables must implement Codex's controls correctly. It does not configure an organization-wide IT policy or change how source is sent to the chosen model provider. See OpenAI's [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) and [managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration) for administrator-enforced controls.

### Permission requests

The common permission-request choices are:

- **Ask when needed** (default): display the requests the agent sends. This does not force a prompt for every command or edit already permitted by its mode.
- **Never ask**: decline permission requests automatically. Already permitted tools can run; this setting does not grant additional access. Agent questions still require an answer.

For **Other agent · ACP**, RODE renders the select/boolean options advertised by that session, including model, reasoning and operating modes. Modern session configuration is preferred, with a legacy mode fallback. Unsupported option types are omitted. Model-related choices appear under Model; modes and other options appear under Permissions. Idle changes wait for acknowledgement and refresh dependent choices without sending a message. Unavailable or rejected saved settings stop submission with an explanation; **Agent settings → Reset saved agent controls** restores a fresh session's defaults. RODE does not invent a universal read-only/full-access switch for ACP agents that expose no such mode.

Codex changes apply to the next turn while retaining the conversation. Returning an explicit model/effort override to its default starts a fresh conversation so old overrides cannot remain active. Executable/provider changes also start a fresh conversation. Transcripts stay in memory; they are never written to preferences. No selector or approval can widen the outer project sandbox's filesystem or network grants.

## Response personalities

Use **Tone**, beside **New chat**, to choose **Default**, **Jackson Lamb** or **Panne**. Default uses the agent's own configured tone.

**Jackson Lamb** is inspired by the [Slow Horses boss](https://www.apple.com/tv-pr/originals/slow-horses/) and [Mick Herron's description of him](https://www.gpb.org/news/2023/11/29/gary-oldman-had-free-rein-in-spy-thriller-slow-horses-now-back-for-season-3): a competent but abrasive, cantankerous veteran, speaking in clipped British English with dry understatement and dark humour. The selected style appears as **Lamb** in the header.

The Lamb hint supplies original tone examples and concrete drafting checks: lead with the finding, change or uncertainty; remove routine process narration and polite padding; use short, concrete sentences; and keep humour tied to an actual defect. It asks the agent to review progress updates and final replies with any sarcastic opening and closing removed, then rewrite bland remaining prose. Routine success needs no joke. Barbs concern the problem, without personal abuse, impersonation or copied dialogue.

**Panne** is a relentlessly critical reviewer who directly challenges your reasoning and the project's output, returning to whether the work is sufficiently thought through, fast enough and competitive. Its never-good-enough stance must stay honest: unsupported claims of inevitable failure become sceptical questions or explicitly subjective reservations. Verified successes and passed checks must still be reported accurately. Criticism concerns decisions and deliverables, not personal worth. Rhetorical challenges do not require answers, add review work or block delivery. Like the other tones, Panne changes response wording only; code, comments, documentation and the actual task retain their normal standards.

The choice is saved per host/project and applies to the next message, including in an existing or restored chat. It works through Codex, Codex local-model mode and ACP. Choosing a style starts no process, sends no message and does not discard conversation context. Stop an active turn before changing it.

For native agents, Rode compares the selected tone with the setting acknowledged by the host. New messages wait while a settings change is pending. If the host retains another tone, a **Tone not applied** message names both settings and holds Send/Queue; waiting host-owned prompts are paused without stopping an active turn. Your selection, draft and queued work remain intact. **Use … tone** explicitly accepts the host's reported setting; otherwise update or restart the host helper before starting a new agent session. Existing jobs are never restarted automatically. This check becomes available after a host reply and does not undo an already-submitted initial turn. It verifies the configured tone, not whether every model response follows the requested voice.

RODE sends a small response-style reminder with **every message**, including follow-ups and resumed chats, alongside the unchanged user task. It explicitly requests the selected voice throughout progress updates, explanations and the final answer, rather than only in the first reply or opening line. It does not change the executable, model, reasoning effort, tools, approval settings, sandbox or project environment. The hint asks for normal task-appropriate code, comments, documentation and other artifacts; only explanatory chat replies should adopt the voice unless explicitly requested otherwise. Explicit output formats and user instructions take precedence. There is no second model call or response-rewriting service.

This is model guidance, so delivery varies by agent/model; prompting cannot guarantee identical model decisions apart from wording. Execution restrictions continue to be enforced independently. Returning to Default explicitly clears earlier RODE tone preferences, without creating a new chat. Recognized style hints are hidden in RODE's displayed history, although the backend may retain them in its own saved conversation. No transcript or custom system-prompt file is added to the project.

The agent core keeps one built-in prompt per personality, edited directly during pre-release development without version numbers or legacy snapshots. History cleanup recognizes the RODE style envelope independently of its wording, so older hints also stay hidden in titles, previews, restored messages and prompt recall. The native agent host generates the hint: an already-running older service retains its loaded prompt, even if the desktop is rebuilt. The host service must also be updated to use changed prompt wording; RODE does not restart running tasks to change their tone. Transport tests verify that the current hint reaches each provider on consecutive turns and after restore; judging the resulting voice requires real model replies.

## Chat history

Click **History** beside the chat status. RODE asks the selected agent on the current project host for saved conversations in this project folder. Filter the loaded titles/previews, use **Load more conversations** for older entries, and select a conversation to restore its recent messages and continue chatting. **Back** or **Cancel** returns to the current chat; **Refresh** reloads the list. Stop an active turn before restoring another conversation.

Use **Delete…** beside an individual chat or **Delete all…** in the history header, then confirm the displayed action. Delete all covers the current host, project folder and backend/provider, including unloaded pages and archived Codex chats; the text filter does not limit it. Open RODE conversations and backend-reported active turns are kept. End an open agent session before deleting its saved history. Deletion never submits a model prompt or deletes project files.

Each row describes its availability: **Saved · Restore chat**, **Open here · Return to chat**, **Open in another window**, **Running in background**, or **Open in another process**. Selecting the current chat returns to it without reopening the backend. Known open chats lead to **Running**, where **Attach** continues a detached RODE session. Host-owned RODE chats are identified when history is refreshed, including idle persistent chats. Ownership in another client may only become known when the backend rejects a restore; that row is then marked as open elsewhere, and other saved chats remain usable.

The temporary history browser is hidden from **Running** until it becomes a restored chat. If its connection closes, restoration, deletion and pagination are disabled until you refresh history; the current chat remains intact.

An “active writer” error means an agent process still has the chat or one of its child chats open, possibly in an idle or detached session. Return to the owning window/client, or use **Running agents… → Attach** for a detached RODE session. To restore or delete its saved history, use **Running → End** for the owning agent, or end the session in the other client, then refresh history and retry. Closing a persistent window leaves its agent running. The main message names the ownership conflict; **Error details** retains the raw failure, and **Startup warnings and backend output** shows additional output separately. A missing system `bwrap` warning is separate from thread ownership; Codex can fall back to its bundled bubblewrap, while RODE's own sandbox availability is shown in the project status.

Codex uses its permanent `thread/delete` operation, which also removes spawned child chats. ACP deletion requires `sessionCapabilities.delete`; whether an ACP agent keeps recoverable storage is up to that agent. Unsupported or older backends explain why deletion is unavailable. RODE updates the list only after the backend acknowledges removal, reports partial failures, and stops remaining operations when browsing is cancelled; already completed deletions remain in effect. Codex deletions, including individual deletions, check active descendants across unloaded and archived pages before removing a parent. Bulk deletion counts confirmed descendant removals once and consumes any already-pending child response before continuing; unconfirmed backend errors still stop deletion. Discovery snapshots at most 4096 scoped chats across 256 metadata pages before making changes; larger or inconsistent lists fail visibly without deleting any chats. Refresh reloads authoritative history after a failure or cancellation.

Codex and Codex local-model history use the agent's saved threads, including conversations created by its CLI or VS Code integration in the same folder. They use separate provider filters. ACP history requires the agent to advertise session listing and loading; unsupported capabilities are explained in the browser. Entries come from the agent's storage visible inside the active sandbox, on the project host—not from the desktop when using SSH. No RODE transcript database or preference-file copy is created. **New chat** does not delete saved conversations.

Listing/loading starts a separate, short-lived agent process without requesting model inference. A successful restore replaces the current chat process; a failure or cancellation leaves it intact. Closing history/the agent panel or changing project, host, sandbox, interpreter or agent settings stops the browser. The current Codex access/approval policy overrides the saved thread's policy; current explicit model/effort choices apply when you continue. ACP controls are applied before the next prompt, using the session's advertised capabilities. The outer project sandbox always remains in force.

RODE displays up to 32 recent Codex turns, 128 messages and 512 KiB of replay; the agent retains the full conversation context. Metadata browsing is limited to 256 conversations and 32 pages. History connections accept protocol lines up to 2 MiB, including after resuming; oversized replies fail visibly. ACP replay shares the display limits. Agents must already have readable saved history; RODE cannot recover conversations that were never persisted by the agent or were deleted. Archiving stays in the agent's own tools.

## Providers

| Provider | Required software on the project host | Configuration |
| --- | --- | --- |
| Codex | Optional `rode-codex` runtime or an installed Codex; authenticate on the project host | Executable defaults to `auto`; optional model; blank model uses the Codex default |
| Codex · local model | Optional runtime or installed Codex and a running Ollama or compatible Responses server | Executable defaults to `auto`, API base URL, and an already installed model name |
| Claude Code · Anthropic | Installed `claude-agent-acp` adapter and Claude authentication on the project host | Adapter defaults to `claude-agent-acp`; optional literal arguments; advertised model, effort and permission controls |
| Other agent · ACP | An agent implementing ACP v1 over stdio, with its own file/command tools | Executable and arguments as a JSON array |

Custom executables can be absolute paths, project-relative paths such as `./tools/my-agent`, or names on PATH. RODE also checks `~/.local/bin`. Arguments are passed directly, without shell expansion. To customize environment variables or launch a special CLI profile, select your own small wrapper script. Other agents and model servers remain user-installed; RODE does not download models, manage accounts, or store API keys.

### Codex

The editor and Codex are separate components. Click **Install Codex** in a new chat or **Agent settings** to install the pinned native [Codex CLI](https://developers.openai.com/codex/cli/) for your user. The optional **`rode-codex`** Debian package and existing Codex executables are also supported. No VS Code, Node.js or npm is required. Leave **Codex executable** set to `auto`. Older saved settings containing `codex` also select this mode. An explicit custom executable overrides discovery; without the optional runtime, an installed Codex on PATH or in `~/.local/bin` remains usable. RODE uses the [app-server protocol](https://developers.openai.com/codex/app-server/) for conversations, command/file tools, approvals, questions and interruption.

The managed runtime includes the main `codex` executable plus its pinned `codex-code-mode-host` and `codex-exec-server` helpers. All three are verified, packaged, deployed over SSH and exposed together inside the project sandbox. No separate Node.js installation is required. If an older RODE installation reports a missing helper, rebuild/update RODE, click **Install Codex**, then choose **New chat** (end an old persistent agent through Running if needed). Explicit installation adds missing verified helpers while retaining an unchanged main executable; changed or unsafe existing files are rejected. An older main-only portable/package bundle is skipped in favor of a verified complete user installation. Discovery never downloads or repairs files automatically. Custom executables remain user managed.

For a local project, authenticate in a terminal with `rode --codex login`. Use `rode --codex --version` to check the bundled version. These commands forward to Codex without starting the editor. Existing Codex authentication/configuration in `~/.codex` remains usable after uninstalling VS Code. Local-model mode does not require OpenAI authentication.

For SSH projects, opening **Model**, sending the first message or explicitly opening **History** can deploy the pinned runtime to a private cache on the project host, using the existing authenticated connection. Transfers are streamed, size/SHA-256 checked, serialized across windows and atomically published. Subsequent starts reuse the verified cache. Credentials are never copied from the desktop. Authenticate on that host using the cached executable at `~/.cache/rode/codex/VERSION/ARCH/RUNTIME_SHA256/codex`, for example with `login --device-auth`. `RODE_CODEX_CACHE` on the host can select another absolute cache location with an owned, non-writable-by-others parent.

The optional package includes its own CPU architecture. **Install Codex** detects an SSH project's host architecture and downloads that runtime to your desktop's user data directory; the normal chat launcher transfers it to the remote cache when needed. Alternatively, prepare it with `python3 scripts/bundle-codex.py --install --architecture aarch64` (or `x86_64`), include it in a portable bundle, or configure an installed executable on that host. When no upstream binary exists, provide a compatible source-built executable if supported, or choose an ACP agent. Missing Codex affects only that integration. RODE does not silently download another runtime or execute the agent on the desktop instead.

Source builds optionally prepare the runtime with `python3 scripts/bundle-codex.py`; this default writes into the checkout's `target/codex/`, discovered by editors in its usual `target/debug/` or `target/release/` directories. Portable distributions put version/architecture folders under `rode-codex/` beside `rode`. Debian's optional package installs them under `/usr/lib/rode/codex/`, also discoverable by Cargo-installed or copied editors. `RODE_CODEX_BUNDLE` selects an explicit prepared **version/architecture directory** containing `codex`, `manifest.json` and the notices.

The optional runtime has its own version and protected checksum manifest, allowing compatible upgrades without rebuilding the editor. Runtime releases still require protocol compatibility checks. The application downloads only after an explicit **Install Codex** click, never during startup, model selection, message submission or history browsing. Discovery and verification happen on workers. Opening **Model** can start a short-lived metadata connection; a conversation starts only after a message or explicit history restore. The binary adds disk/download size only when installed and is not loaded into the editor's idle process.

### Installing Codex for a Cargo-installed editor

Install RODE from the source checkout:

```sh
cargo xtask install
rode /path/to/project
```

Open **View → Agent chat** (or **Ctrl+Shift+A**) and click **Install Codex**. It also appears in **Agent settings** for an existing conversation, for both Codex providers. The native Rust installer needs no Python script or administrator access. It shows download/extraction progress and **Cancel**, verifies the pinned archive, executable and embedded license notices, and installs under `$XDG_DATA_HOME/rode/codex/VERSION/ARCH` (default `~/.local/share/rode/codex/VERSION/ARCH`). Empty or relative `XDG_DATA_HOME` values use the default. This keeps managed executables separate from `~/.codex` / `CODEX_HOME`, authentication and configuration.

The protected, atomically updated `manifest.json` selects the complete verified runtime. Concurrent RODE windows and the optional preparation script serialize publication. Cancellation, failed downloads and failed verification leave the previous selector intact; existing verified files are reused without a download. Damaged or different files in the destination are reported rather than overwritten. The installer removes group/world write permission from the owned RODE application-data parent when needed, preserving existing preferences and locks; runtime roots and files retain their strict safety checks. Changing the project/host or executable/provider cancels that window's setup. Closing RODE cancels setup and waits for temporary-file/lock cleanup before exiting. Installation only prepares assets: it never starts a chat, signs in, downloads a model or changes project sandbox grants. SSH architecture discovery requires the existing authenticated connection, but runtime downloads need internet only on the desktop.

Keep **Codex executable** set to `auto`, and use `rode --codex login` if authentication is needed; `rode --codex --version` checks discovery without opening the editor. Reinstalling/updating the editor does not remove the user runtime. An existing portable or installation-relative runtime takes precedence over the user installation; `RODE_CODEX_BUNDLE` takes precedence over all automatic locations. Custom executables and an explicit bundle override disable the UI installer until cleared. The UI installs the version pinned by this editor, not an automatically discovered latest release.

For scripted/offline preparation, `python3 scripts/bundle-codex.py --install` remains available and uses the same user directory and install lock. It can reuse a previously cached archive. Add `--architecture aarch64` / `x86_64` for another host. `--install` cannot be combined with `--output`; without either option, preparation uses the checkout's cache. To use an already prepared directory without installing it, set `RODE_CODEX_BUNDLE` to the absolute version/architecture directory printed by the command when launching RODE.

Codex defaults to `on-request` approval and workspace-write access; the visible Model/Access controls can override these per project. Existing CLI instructions, managed restrictions, configuration, and authentication still apply. You may need to grant access to a custom `CODEX_HOME`, executable, or runtime through the sandbox settings. RODE does not edit the CLI's configuration files.

### Local models with Ollama

Use Codex as the coding agent and Ollama as the model server. This keeps planning, file editing, and command execution in the agent, with inference served locally. Ollama documents a [Codex integration using its Responses API](https://docs.ollama.com/integrations/codex).

1. Use the optional Codex runtime or an installed Codex, and install Ollama on the appropriate host. Start Ollama, for example with `ollama serve`, if it is not already running.
2. Install a tool-capable model of your choice explicitly. Use `ollama list` to see installed model names. The model must fit your hardware; Ollama recommends at least a 64k context window for Codex.
3. In RODE, choose **Codex · local model**. Set **Local model API base URL** to `http://127.0.0.1:11434/v1` and enter the exact installed model name.
4. Send a message. RODE selects a dedicated `rode_local` Responses provider without requiring OpenAI authentication or falling back to an OpenAI model. Web search is disabled for this provider.

**`localhost` means the project host.** For an SSH project, that endpoint is on the remote computer. If your server is on your desktop, use an explicitly configured SSH reverse tunnel or another address reachable from the remote host. RODE does not create model tunnels. A server offering only `/v1/chat/completions` is insufficient; it must implement Codex-compatible `/v1/responses` streaming and tools. Other local servers can use the same settings when they meet that interface. Select an actual local model if you want local inference; a server may also expose cloud-backed model names.

The model server is a separately managed service; RODE does not start it inside the project sandbox. With **Use project network policy**, even a loopback model server requires **Allow network access**. Alternatively, [Model connection only](#model-connection-with-offline-tools) lets the controller contact that server while native commands keep the project's offline policy.

### Claude Code / Anthropic

Choose **Claude Code · Anthropic** in the chat provider selector. RODE uses the maintained [Claude Agent SDK ACP adapter](https://github.com/agentclientprotocol/claude-agent-acp), sharing the existing chat, attachments, approvals, history, recovery, queues and persistent-agent UI. Codex is not required for this provider. The adapter uses Claude's own coding tools; it runs on the captured project host inside the selected outer sandbox.

1. Install the adapter on that host. With Node.js 22 or newer, the tested npm release is `npm install --global @agentclientprotocol/claude-agent-acp@0.100.0`. Upstream also publishes [standalone executables](https://github.com/agentclientprotocol/claude-agent-acp/releases), which include their Claude CLI and need no Node.js installation; keep the two executables together.
2. Authenticate there before sending a message: run `claude-agent-acp --cli` in a terminal and use Claude's `/login`, or provide `ANTHROPIC_API_KEY` in the host environment. The adapter's `--cli` mode forwards to its bundled Claude CLI. `CLAUDE_CODE_EXECUTABLE` can select a separately installed Claude CLI. RODE does not store API keys, copy desktop credentials to SSH hosts, or perform an interactive login inside chat.
3. Leave **Claude ACP adapter on this host** at `claude-agent-acp`, or set an installed executable/wrapper path. Optional arguments use a JSON array and are passed literally. RODE never runs `npx` or installs the adapter automatically when selecting the provider, browsing history or sending a prompt.
4. Send a message. **Model** and **Permissions** show the adapter's advertised model, effort and mode choices once the session is initialized; saved choices are acknowledged before the next prompt. These settings are separate from **Other agent · ACP**, so switching providers does not overwrite another adapter's executable, arguments or controls.

For SSH projects, install/authenticate on the remote host. With sandboxing enabled, explicitly grant the adapter/Node or standalone runtime paths and Claude's configuration/history paths (normally `~/.claude` and `~/.claude.json`) as required by that installation. Credentials and writable caches remain subject to your project grants. **Edit project files only** is a Codex-specific mode and cannot be selected for Claude or another ACP agent. Claude's advertised permission modes and RODE's request-approval setting remain available; neither can widen the outer sandbox.

ACP v1 capabilities determine history listing/loading/deletion, images and selector availability. The common ACP limitations below also apply; RODE does not advertise client filesystem/terminal tools or form elicitation. Session protocol 13 selects a matching host controller for the named Claude settings while preserving existing older service generations and their running jobs. Rebuild/update the native helper together with the editor.

### Other agents

Choose **Other agent · ACP** and supply the installed agent's ACP command. For example, arguments `['acp', '--verbose']` must be entered as valid JSON: `["acp", "--verbose"]`. Use the agent's documented ACP launch arguments, rather than its ordinary interactive terminal command. See the [ACP agent directory](https://agentclientprotocol.com/get-started/agents) for implementations and adapters.

RODE implements ACP **v1** initialization, project sessions, streamed text/tool updates, permission choices, and cancellation. It advertises no client filesystem or terminal capabilities: the agent must execute its own tools inside its process tree. Unsupported client filesystem, terminal, authentication, custom-tool, and elicitation requests fail explicitly. Authenticate the agent beforehand. Arbitrary interactive CLIs and the ACP v2 draft are not supported by this chat client; ordinary agent CLIs remain usable in the integrated terminal.

## Sandbox, edits, and lifecycle

By default, an active [project sandbox](sandbox.md) encloses the whole agent process and its tool children, locally or over SSH. It uses the same folder grants, writable caches, network setting, and selected Python environment as other project commands. Approving an agent request cannot widen those outer mounts or network restrictions. Codex is told when a writable external sandbox is enforcing access, avoiding nested isolation. Read-only projects retain Codex read-only mode as well as the outer filesystem restrictions. **Model connection only** keeps those filesystem restrictions but gives the trusted controller a network exception and uses native offline tools instead of Codex's execution tools; project environment providers are not evaluated in that network-enabled controller.

Bundled Codex adds only its verified runtime directory as a read-only tool grant: mounted at `/rode-codex` with bubblewrap, or kept at its real path with Landlock. Other cached files and the rest of home are not exposed by this grant. Preparing/deploying the runtime happens on the host; execution always uses the captured project sandbox. Custom executables retain the existing explicit grant requirements.

When the selected sandbox backend is unavailable, the panel reports normal mode with the same visible fallback as the rest of the project. Choose bubblewrap or Landlock in the [sandbox settings](sandbox.md); their isolation limits differ. No later agent failure triggers a retry outside an active sandbox. `~/.codex` is a shared writable path by default; other agents' settings, credentials, runtimes, and caches may need explicit grants. Their child processes inherit the project host environment.

Agents read files from disk. The composer shows an unsaved-buffer notice with **Save all**; sending a message does not save or upload unsaved buffers. After a turn, clean editor files refresh using version checks while dirty buffers stay intact. If both you and the agent change the same file, the normal save conflict protections apply. Review agent changes through the existing Git panel.

**Stop** requests interruption, then closes an unresponsive process after three seconds; a second click closes it immediately. **Disconnect** closes an idle nonpersistent agent. **New chat**, project/sandbox/interpreter changes and editor exit release the current view: nonpersistent agents stop, while persistent agents retain their original environment until explicitly ended. Closing the chat panel only hides it. Agent shutdown never interrupts the project terminal or shared SSH master.

Provider settings are saved immediately per host/project. Changing the executable/provider starts a new conversation on the next send; an existing persistent session keeps its original executable and environment. RODE keeps a bounded conversation in memory, without saving transcripts. Use **Running** for a live detached session or **History** for conversations saved by the backend. URLs and command arguments are saved preferences, so use the CLI's login/environment for secrets.

### Recovering after an agent failure

If an agent exits unexpectedly or exceeds a transport limit, RODE stops its connection and offers **Recover agent** in the chat panel. Your draft, visible messages, queued prompts and their captured attachments are kept. The host controller stays available, including through **Running** for persistent agents. Recovery uses the original project host and access policy.

**Recover agent** reconnects to the saved backend conversation without sending an inference request. It never repeats the interrupted prompt. Check whether that prompt completed or changed files before deciding what to send next. The queue stays paused until you choose **Resume queue**.

If the backend cannot restore the conversation, choose **Recovery options → Start new context · keep queue**. Earlier messages remain visible but are not sent as context to the new conversation; your draft and queued work remain available. ACP reconnection requires the backend's `loadSession` capability. File-only agents require a new context to verify their configuration again and recreate their confined file tools. **New chat** and **End** retain their existing lifecycle behavior.

Typed messages are limited to 32 KiB, agent protocol lines to 4 MiB (2 MiB for history connections), stderr diagnostic lines to 1 MiB, and displayed history to 128 messages / 512 KiB. Line limits include the trailing newline. RODE retains up to 8 KiB of stderr diagnostics for error reporting. File payloads have the separate limits described above. Large tool output is truncated explicitly. Interactive login in chat is not implemented. Transport tests use deterministic peers; a real Codex compatibility test is available in the [development guide](development.md).
